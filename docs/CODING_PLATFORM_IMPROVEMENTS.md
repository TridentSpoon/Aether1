# AETHER CODE improvement backlog

This backlog turns the coding-platform assessment into work that can be verified. It is ordered by dependency: task continuity and observable execution come before broader capabilities. Each item needs its own implementation and focused validation; this document does not claim any of them is shipped.

## 1. Resume the right engine session for each task

Capture OpenCode's actual session ID from structured run events, persist it with the AETHER CODE task, and pass it back with `--session` on the next run. A newly created task must start a new engine session. Switching tasks, restarting Aether1, deleting a task, and a failed first run must not route work into another task's session. Keep the engine's shared provider cache while isolating conversation IDs. Verify with two interleaved tasks and a restart.

## 2. Show structured tool activity

Consume the same structured engine events used for item 1. Display tool name, target, start, completion or failure, and a concise result in the coding panel. Keep full diagnostics accessible and ensure both Tauri IPC and HTTP deliver the same event contract. Verify that a file edit and a failing command appear in the correct task in real time.

## 3. Establish a repeatable coding evaluation

Create a fixed, versioned set of small, medium, and long tasks against disposable repository fixtures. Record model and version, machine, prompt, elapsed time, outcome, tests, human intervention, and whether recovery was needed. Run the baseline against Aether1 and the same underlying OpenCode model directly, so the harness's contribution is measurable. Never run the evaluation against the operator's working tree.

## 4. Make checkpoints inspectable and restorable

Show the latest checkpoint's timestamp, reason, and affected files in the coding panel. Before restore, show what will be restored and what new files will remain; reuse `code_checkpoint`'s additive revert path. Verify with tracked, staged, untracked, and newly created files, including a failed restore.

## 5. Provide Windows confinement

Implement an OS-enforced Windows execution boundary for the nominated workspace, hidden credentials, controlled network, and process cleanup. Preserve the current refusal until it can enforce those properties. Verify with Windows-specific escape tests and `cargo check --all-targets` in CI.

## 6. Preserve useful context on long tasks

Use the task's engine session as the primary conversation history. If the engine compacts or a local model has a short context window, retain inspectable decisions, file references, and outstanding work for that task. Verify a follow-up after enough turns to exceed the current six-turn panel history.

## 7. Expose an action journal

Record each tool action with task ID, timestamp, target, outcome, and checkpoint reference where relevant. Surface it in the coding panel and make it searchable by task. The journal must report actual tool events rather than prose generated by the model.

## 8. Add bounded host and browser tools

Define narrow host reads and operations through explicit tools, with approval for host mutation. Run browser automation in its own sandbox and keep downloads inside the nominated workspace boundary. Apply the network rules in `HOW_THIS_IS_BUILT.md` before adding any outbound path. Verify that credentials and unrelated host files remain inaccessible.

## 9. Test the installed experience end to end

On each supported platform, install a release artifact into a clean environment, select a local model, open a project, complete a coding task, inspect its actions, restart and continue it, and restore a checkpoint. Record unsupported capability as a clear refusal. Keep this separate from source-tree tests.

## Release gates for each implementation

Run `for s in scripts/check_*.sh; do bash "$s" || echo "FAILED: $s"; done`, focused Rust or frontend checks, and the relevant platform CI jobs. Preserve pre-existing working-tree changes. Report any guard failure and any test that requires a live model or unavailable platform.
